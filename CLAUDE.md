# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — type-check (`tsc -b`) then production build via Vite
- `npm run lint` — ESLint over the whole project
- `npm run preview` — preview the production build locally

There is no test runner configured in this project.

## Architecture 

NEXUS ("career-os") is a personal dashboard SPA: React 19 + TypeScript + Vite, Tailwind v4 (via `@tailwindcss/vite`, config lives in `src/index.css` under `@theme`, not a `tailwind.config.js`), React Router v7, and Supabase for auth + data.

### Reuse shared components before writing new ones

**Before building a new UI piece, check `src/components/` first — a strong project goal is maximizing reuse across modules rather than re-implementing the same widget per feature.** Several near-identical components already got duplicated once per module (e.g. four copies of `ConfirmDialog.tsx`) before being consolidated back into `src/components/`; don't reintroduce that pattern. Current shared components:

- `ConfirmDialog` — standard delete/destructive-action confirmation modal (title, message, Cancel/Confirm). Used everywhere something can be deleted.
- `RichTextEditor` (+ exported `RICH_CONTENT_CLASS`) — contentEditable-based rich text editor (bold, uppercase, color, bullets, inline image upload via a passed-in `uploadImage` fn). Render its saved HTML read-only with `dangerouslySetInnerHTML` wrapped in `RICH_CONTENT_CLASS` so bullets/images look identical in edit and view mode.
- `CodeBlock` — collapsible code snippet; pass `onChange` to make it an editable input, omit it for a read-only collapsible viewer.
- `TableBlock` — collapsible free-form spreadsheet-like table block, same editable-via-`onChange` / read-only-without-it convention as `CodeBlock`.
- `ShortcutsBar` / `ShortcutTile` — the icon-grid "quick links" row (with add/reorder/delete, favicon auto-detection, custom icon upload) used on the Dashboard, Grades, and Work Tracker pages, each backed by its own `*_shortcuts` table.
- `BackNav` — the "‹ PARENT / CURRENT" header for nested pages (square back button + uppercase breadcrumb). Use it on any page that sits under another one instead of a plain "← Back" link.
- `ContextLibrary` — folders of markdown context docs with an edit/split/preview editor, autosave and "Copy all", scoped by a `section` prop (a module id, e.g. Content's "AI context" tab uses `"content"`). Data goes through `src/lib/contextDocs.ts` (tables `knowledge_folders` / `knowledge_docs`, names kept from the removed Knowledge module). Pass `starter` folders+templates for the empty state. Reach for it whenever a module needs AI-readable context docs; don't create new doc tables.
- `CollapseToggle` + `src/hooks/useCollapsed.ts` — chevron button to minimize/expand a block, with the choice remembered per browser (`localStorage` key `collapse:<id>`). The Content planner uses it on every horizontal block (upcoming weeks, theme & brief, days, month calendar, Ready to post, Idea bank); reuse it for any other collapsible section.
- `SectionContextButton` — the fixed "CONTEXT" tab docked to the left edge of the viewport, mounted once in `AppLayout` so it appears on every module automatically. See "Section context" below.

The **block pattern** — a title plus optional `RichTextEditor` + `CodeBlock` + `TableBlock` — is the standard shape for "flexible free-form entry" features (see `work_general_info`, `project_entries`, `work_endpoints`). Reach for that combination again rather than inventing a new entry format when a module needs open-ended notes.

### Module system

The app is organized as a fixed set of "modules" (Motorcycle, Medical, Content, Grades, Project Management, Pipeline, Finance, Work Tracker), each a self-contained vertical slice under `src/features/<name>/`. A module typically contains:
- `<Name>Page.tsx` — top-level page with its own tab state, fetches data in `useEffect` and passes it down
- `api.ts` — direct Supabase queries (no shared data-fetching layer/React Query; each module calls `supabase.from(...)` itself and throws on `error`)
- `types.ts` — row types matching Supabase tables, plus any pure helper functions for that domain (e.g. grade-point math in `grades/types.ts`)
- `tabs/` — sub-views switched by local tab state within the page
- `components/` — module-scoped UI pieces (only for things genuinely specific to that module — check `src/components/` first, see above)

`src/lib/modules.ts` (`MODULES`) is the single source of truth for module metadata (id, name, route path, description, icon) driving both the dashboard cards, the nav in `AppLayout`, and the section key `SectionContextButton` uses. Adding a module means: add an entry here, add a route in `src/app/router.tsx`, and add the `src/features/<name>/` slice.

All modules are now wired to Supabase (the earlier placeholder mock data in `projects` has been replaced by a real `personal_projects` + `project_entries` backend). `grades`, `medical`, and `work` remain good reference patterns for a fully wired module (api.ts + types.ts + tabs).

A few modules go one level deeper with a **nested workspace** pattern: a list page (`ProjectsPage.tsx`) links into a per-item page with its own route param and its own tab bar (`ProjectWorkspacePage.tsx` at `/projects/:id`, tabs: Tablero/Mensajes/Resumen/Links/Credenciales/Expediente/Entradas/Diseño). The Tablero tab is a per-project Kanban (`project_board_columns` + `project_board_tasks`, user-created columns, drag via `@hello-pangea/dnd`); Mensajes is a client↔owner conversation (`project_messages`, realtime + polling fallback, unread count from `project_message_reads`). Expediente is admin-made blocks of documents/notes or payments (`project_dossier_sections` + `project_dossier_payments`, files in the private `project-dossier` bucket via signed URLs): a client sees a block only if both the per-project switch (`project_dossier_settings.visible`) and that block's `visible_to_client` are on, enforced by RLS, and only the admin writes, even if the client has edit on `projects`. Clients see the project read-only unless they have edit on `projects`, see shared Credenciales and Links but never their "Privada" sections, and only the owner can delete the project. Reach for this when a module's items each need a substantial amount of their own sub-content, rather than cramming it into an expandable card.

**Content** (`src/features/content/`) is a "Content Studio" built around a **weekly planner** keyed by ISO week (`'YYYY-Www'`, Mon–Sun; helpers in `content/types.ts`). All tabs (Planner / Idea board / Finished / Published / Stats / Categories / AI context) share one store, `useContentStudio()`, instead of fetching per tab. An idea (`content_ideas`) is a "piece" once it has a `scheduled_date`; its week is derived from that date (no FK), `schedule_order` orders it within its day, and ideas with no date form the "banco de ideas". `content_weeks` holds each week's plan (one row per `user_id` + `week_key`, upserted on first edit: `title`, `goal` = the brief the AI reads, `status` draft/approved/done). A piece is finished when `script_done && recorded && edited`; it's **published** once it has a row in `content_publications` (BLOQUE 25: one row per piece × platform with date and URL — **no metrics on it**). The Finished tab lists finished-but-not-posted; Published lists the posts with their latest numbers, and editing a cell saves today's snapshot. **Stats** (BLOQUE 27) is the analytics tab: Week/Month/Range × TikTok/Instagram/Both, KPI cards with delta vs. the previous period and day coverage, funnel views → profile views → followers → leads, hand-written SVG daily chart (TikTok `#0ea5c6` / Instagram `#e0457b`, validated with the dataviz script), top 5 by views and by conversion ((follows + leads) per 1k views, falling back to profile views), averages by format/style, best-times heatmap, a rule-based written summary and leads by piece. Data: `content_post_metrics` (dated snapshots per publication, unique per day, newest = current), `content_account_daily` (account totals per day × platform), `content_period_totals` (BLOQUE 28: a platform's own total for a range, e.g. "last 7 days", stored as is and **never split into days**; per platform and metric Stats uses (1) the sum of loaded days, else (2) a total for exactly the period, else (3) the total that overlaps it most, labelled "Period total · Nov 7–13 (partly outside)" — and shows no delta when a partial total is involved), a "Followers" card with the latest `followers_total` and its "as of" date, `content_active_times` (0 = Monday, Caracas hour), and leads = `pipeline_deals` with `source` in tiktok/instagram or a `source_idea_id` (BLOQUE 26). **A metric nobody entered is `null` and shows "No data", never 0.** All math lives in pure functions in `content/stats.ts` (`metricsSummary` also feeds the "Plan with AI" prompt); manual entry is the "Log metrics" sheet (Account / Post / Lead). MCP: `log_account_metrics`, `log_period_totals`, `log_post_metrics`, `log_active_times`, `get_analytics_summary` (same day/total rule, reported per metric in `origen`) (Claude loads numbers from TikTok/Instagram screenshots sent in the chat). Phase 2 (not built): TikTok Display API + Instagram Graph API sync from an Edge Function, tokens never in the client. `format` is where it's published (keys `reel|carrusel|post|historia|video|texto`, labels Reel/Carousel/Post/Story/Long video/Blog) and `style` (BLOQUE 24) is how it's produced (`animado|humano|noticia|foto`, `''` = not set); the idea board and Finished share a format/style filter (`components/PieceFilters`). Columns added by later blocks are optional in the client: rows are normalized in `api.ts` and the idea modal only sends changed fields, so the UI keeps working before a block is run. The planner has a **Week / Month** toggle (remembered in `localStorage`): the week view is the strip of upcoming weeks (past weeks open in the "Last weeks" modal) plus the 7-day grid; the month view is `components/MonthCalendar.tsx`, a Google-Calendar-style grid inside the same `DragDropContext`, so pieces drag between days and the shared strips below the calendar in both views: **"Ready to post"** (finished pieces with no date; only accepts finished pieces) and the **idea bank** (unfinished, no date). `content_ideas.do_not_publish` (BLOQUE 23) keeps a piece out of both strips, shows it dimmed with a badge on the board, and the MCP excludes it (`get_content_week` omits it, `plan_content_week` rejects it); the idea modal sends only changed fields so saves never write a column the DB may not have yet. The weekly publishing rhythm (set 2026-11-14) is Mon animated video (stock) · Wed carousel · Thu animated video (stock) · Sat human reel (Andrés on camera) · Sun "Noticias de la semana #n" (animated news); finished videos come from the sibling `../videos` project (`videos/out/<id>/<id>.mp4`). The W46–W53 plan is loaded in the DB. Data changes can be made directly with the MCP server's own login (`mcp-server/.env`, RLS applies) from a one-off Node script; only schema changes need `PENDIENTE.sql`. The "Contexto IA" tab is a `ContextLibrary` with `section="content"` (starter templates in `content/contextTemplates.ts`). The AI reads that context and plans weeks through the NEXUS MCP server (`mcp-server/index.js`: `get_content_context`, `write_content_context`, `get_content_week`, `plan_content_week`); the planner's "Planear con IA" button copies a prompt for those tools.

**Pipeline** (`src/features/pipeline/`, route `/pipeline`) is client follow-up with a "guardian": `pipeline_stages` (each with `max_days` without movement, a `rule` in words and a `message_template` with `{nombre}`), `pipeline_deals` (client/lead, stage, `last_activity_at`, `note`, value, `status` open/won/lost, `suggested_message`, lead origin `source` + `source_idea_id` → the content piece) and `pipeline_activity` (history, `actor` andres|agent) — BLOQUE 26, which also seeds the 4 default stages. `healthOf()` in `pipeline/types.ts` is the rule: past `max_days` = needs attention, on the last allowed day = watch. The page is a drag-and-drop board per stage (moving a deal to another stage restarts its clock) plus the guardian panel (most overdue deal, its numbers and the proposed message to copy / open in WhatsApp; "I followed up" restarts the clock). The guardian never sends anything. Agents use `pipeline_review` and `pipeline_update` in `mcp-server/index.js` (their changes are logged with actor `agent`); the tables are also in `crud.js`.

**BRAIN** (`src/features/brain/BrainPage.tsx`, route `/brain`) is the single library of markdown context every agent reads over MCP. It is deliberately **not a module**: `BRAIN_MODULE` sits next to `ADMIN_MODULE` in `src/lib/modules.ts` (outside `MODULES`), so it never appears on the dashboard board and can't be regrouped — but the Admin panel lists it after the modules so a user can be granted View / Edit with module id `"brain"` (BLOQUE 29 rewrote the `knowledge_*` RLS: section `brain` follows the `brain` permission, section `content` the `content` one). View = read-only page; Edit = create/edit docs and folders; deleting and "Connect an agent" stay admin-only. The button shows for `isAdmin || canView("brain")`; `AppLayout` renders it as a fixed button right after the nav (Admin is always the nav's last item) and in the mobile drawer, and `CommandPalette` lists it. Data lives in `knowledge_folders` / `knowledge_docs` with `section = "brain"` via `src/lib/contextDocs.ts` (starter folders/templates in `brain/brainTemplates.ts`). **BRAIN replaced the old Knowledge module** (removed 2026-11-14; its 5 folders / 12 docs were moved to `section = "brain"`), so there is no general `section = ""` library any more; the chat worker's context (`mcp-server/context.js`), `get_schedule` and `file_attachment` (destination `"brain"`) all read/write BRAIN, and the old `knowledge` / `write_knowledge` MCP tools are gone. The page is a three-pane docs workspace (searchable folder tree, Read/Edit/Split reader with autosave, heading outline), separate from `ContextLibrary` because it needs that layout. Agents use `brain` (no args = index; `doc` / `folder` / `search` / `full`) and `brain_write` in `mcp-server/index.js`; `get_schedule` tells them to read BRAIN first.

**Generic CRUD tools** (`mcp-server/crud.js`, registered at the end of `index.js`): `nexus_tables`, `nexus_list`, `nexus_create`, `nexus_update` (one row by id), `nexus_delete` (by ids, requires `confirm: true`). They only reach the tables in its `TABLES` map (admin/permissions, chat, `site_credentials` and the private project tables are left out), redact any password/secret/token key as `[oculto]` and reject writes that contain that marker. Add a new module table to `TABLES` with its columns. The DESJ app (`../DESJ`) uses this server from its worker, only for Andrés's DESJ account, so he can say "DESJ, agrega una tarea al tablero de X". `/content`, `/brain`, `/pipeline` and the dashboard (`/`, exact match) are in `WIDE_ROUTES` in `AppLayout`, so the 7-day grid and the dashboard's side cards + chat get a wider container.

**Dashboard for other accounts:** `DASHBOARD_MODULE` (id `"dashboard"`, in `src/lib/modules.ts`, outside `MODULES`) is listed first in the Admin panel. View on it shows the main screen (quick cards filtered by `canView`, chat) to that account. The chat worker logs in as the admin and answers those accounts with the **same full access** (Andrés's explicit decision); `worker.js` `chatAllowed()` refuses any account that isn't active with `dashboard` view, replies are written with the message owner's `user_id`, and the hourly/daily caps count every reply. BLOQUE 30 adds admin-only read/insert/update policies on `chat_messages` / `chat_conversations` and admin read on `chat-files`; `getConversations()` filters by the current user so the admin's list never mixes in others' chats.

### Section context ("CONTEXT" button)

Every module page gets a free-text scratchpad, without any per-page wiring: `SectionContextButton` is mounted once in `AppLayout.tsx` and renders a fixed tab on the left edge of the viewport on every route. Clicking it opens a modal with an editable textarea (paste-anything) plus Copy and Save. The note is scoped by matching `location.pathname` against `MODULES` (falls back to `"dashboard"` on `/`) and persisted via `src/lib/sectionContext.ts` against the `section_notes` table (one row per `user_id` + `section`, upserted on save). Don't add bespoke "notes" fields to a module when this already covers the same need.

### Routing & auth

- `src/app/router.tsx` defines all routes and wraps the authenticated tree in a `ProtectedRoute` that reads `useAuth()` and redirects to `/login` when there's no session.
- `src/hooks/useAuth.tsx` is a context provider (mounted once in `main.tsx`) wrapping Supabase's `auth.getSession()` / `onAuthStateChange`.
- `src/lib/supabase.ts` creates the single Supabase client from `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (throws at import time if missing — set these in `.env.local`).
- `src/app/layout/AppLayout.tsx` is the authenticated shell (topbar, mobile drawer nav, sign-out) rendered around `<Outlet />`. Note: `src/app/AppLayout.tsx` (one level up, no `layout/`) is a stale duplicate not referenced by the router — don't edit it by mistake.
- `src/App.tsx` is likewise unused dead code; the real entry tree is `main.tsx` → `AuthProvider` → `RouterProvider`.

### UI language: English

**All UI copy is English** (decided 2026-11-13). The Content module is fully translated; the other modules are still Spanish and will be migrated later, so don't mix languages inside one screen. Write any new or touched UI text in English.
- What the *user writes* stays in Spanish: ideas, hooks, scripts, context docs, seeded templates and data in `PENDIENTE.sql` (his audience is LatAm). Only labels, buttons, placeholders, empty states and dialogs are English.
- Shared components that may be rendered by both translated and untranslated screens take a `lang` prop with a strings dictionary instead of being duplicated (see `ContextLibrary`: defaults to `"en"`, `"es"` still available).
- DB values keep their original keys (format keys `carrusel`/`historia`/`texto`, statuses, section ids); only their labels are translated, since the MCP server and existing rows use them.

### Styling conventions

Design tokens (`--color-background`, `--color-surface`, `--color-primary`, `--color-muted`, etc.) are defined once in `src/index.css` and consumed as Tailwind utility classes (`bg-surface`, `text-muted`, `border-border`, ...). Reuse these tokens rather than introducing raw colors, so all modules share the same dark theme.

### Supabase data layer

There is no `supabase/` migrations directory or CLI setup in this repo — schema changes are applied by hand against the live project via the SQL editor or the Supabase MCP connector (`apply_migration`), not tracked as files. Keep this doc's description of the schema in sync manually when you add/change tables.

- **The app's real project ref is `dmhlbgdakispkgbucgmq`** (read `VITE_SUPABASE_URL` in `.env.local` to confirm). The Supabase MCP connector is authorized per-organization from the claude.ai Connectors settings and may be pointed at a *different* Supabase project/org than this app — always cross-check `list_projects`' project id against `.env.local` before running any migration against it, don't assume the only project it can see is the right one.
- Every table has `user_id uuid not null references auth.users(id) on delete cascade` and RLS enabled. Since the admin panel landed, the four policies are **not** plain `auth.uid() = user_id` any more — a new data table gets:
  - select: `user_id = auth.uid() or nexus_can_view('<module id>')`
  - insert: `user_id = auth.uid() and (nexus_is_admin() or nexus_can_edit('<module id>'))`
  - update: `user_id = auth.uid() or nexus_can_edit('<module id>')`
  - delete: `user_id = auth.uid()` — only the owner ever deletes
  All four are named `"nexus read" / "nexus insert" / "nexus update" / "nexus delete"`, so BLOQUE 4 of `PENDIENTE.sql` can drop and recreate them idempotently. Add the new table to that block's `(table, module)` list. Tables that are private per account — `dashboard_*`, `pill_tracker_*`, `section_notes`, `chat_messages`, `project_private_credentials` / `project_private_links` (the "Privada" sections of Credenciales and Links) — keep the old `auth.uid() = user_id` on all four.
- Repeatable/array fields (headers, resources, platforms, category_ids, tech_stack, milestones, ...) are stored as `jsonb not null default '[]'::jsonb`, normalized back to typed arrays in `api.ts` (`Array.isArray(...) ? ... : []`) since Supabase returns raw JSON. Optional text fields default to `''`, not `null`.
- Storage buckets are public (e.g. `work-files`, `shortcut-icons`) so uploaded image/icon URLs can be embedded directly without re-signing on every render. The exceptions hold sensitive files and use signed URLs: `chat-files`, `project-dossier`.
